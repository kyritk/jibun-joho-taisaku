# 脅威モデル（じぶんの情報対策）

作成日：2026-11-07。対象：フェーズ1（GitHub Pages で公開する静的サイト）。
このツールは「漏えいした人が、次に何をすべきか」を伝えるものなので、**最大の被害は、利用者を間違った行動（偽の電話番号にかける、偽サイトでパスワードを入れる）に導くこと**である。可用性やパフォーマンスより、表示する内容の正しさと、サイト自体が攻撃の踏み台にならないことを優先する。

## 1. 守るもの（資産）

| 資産 | 内容 | 失われたときの影響 |
| --- | --- | --- |
| A1 表示内容の正しさ | 事案の事実、やることカード、電話番号、URL | 利用者が詐欺に誘導される。信頼の喪失 |
| A2 利用者の端末内データ | 選んだサービス、カードの完了状態、最終確認日時（localStorage） | 「どのサービスを使っているか」が漏れる。単体では被害は小さいが、標的型詐欺の材料になりうる |
| A3 サイトの正当性 | 「このURLが本物」であること | 偽サイトが本物として広まる |
| A4 リポジトリと公開パイプライン | GitHub リポジトリ、Actions、Pages | 改ざんされた内容が自動で公開される |
| A5 承認者のアカウント | GitHub アカウント（kyritk） | A1・A4 のすべてが崩れる |

**持たないもの**：利用者の氏名、メールアドレス、カード番号、本人確認書類。サーバー側に利用者データを一切持たない（企画書どおり）。持たないことが最大の防御である。

## 2. 信頼境界とデータの流れ

```
[企業の公式発表] --(人が読む)--> [LLM下書き] --(PR)--> [開発者の目視承認 = main へのマージ]
                                                              |
                                                     [GitHub Actions: 検証 → ビルド]
                                                              |
                                                     [GitHub Pages: 静的ファイル]
                                                              |
                                              [利用者のブラウザ] --(localStorage)--> 端末内のみ
```

信頼境界は3つ。
1. **外部の情報 → リポジトリ**：公式発表、LLMの出力、第三者のPR。すべて「信用しない入力」。承認（マージ）で初めて信用する。
2. **リポジトリ → 公開**：main にあるものは信用する。ただし自動化（Actions）が改ざん経路にならないようにする。
3. **公開サイト → ブラウザ**：配信されたHTML/JS/JSONは信用するが、ブラウザ側で文字列をHTMLとして解釈する経路を残さない。

## 3. 脅威と対策

各脅威に対して「受け入れる」「対策する」を明記する。対策の実装状況は 4 章。

### T1 偽の連絡先・偽のURLを表示させる（A1）

| 経路 | 対策 |
| --- | --- |
| 第三者のPRで電話番号やURLを差し替える | main への直接push禁止、PR必須、CI の検証必須。**URLの許可リスト**（`data/official-domains.json`）に無いホストはビルド失敗 |
| LLMの下書きが間違う（幻覚） | 下書きは `drafts/` に置き、承認者が公式発表と照合して `approved/` へ移す。CIは `approved/` だけをビルドする |
| 承認者が見落とす | 承認時に `announcements[].url` を必ず開く運用。「未検証」の語を含むデータは警告 |
| 企業の通知メールの番号を転記してしまう | カード設計の原則4。連絡先は `official_contacts` に登録したものだけ表示し、事案側の `official_contact` も公式発表に書かれたものに限る |

### T2 サイトを改ざんして悪意あるスクリプトを動かす（A1, A2, A3）

| 経路 | 対策 |
| --- | --- |
| 承認者アカウントの乗っ取り | GitHub の2要素認証（必須）。パスキー推奨。トークンのスコープ最小化 |
| GitHub Actions の改ざん・サプライチェーン | 使用するアクションを**コミットSHAで固定**。`permissions` を最小（`contents: read`、デプロイは `pages: write` と `id-token: write` のみ）。`pull_request_target` を使わない。シークレットを持たない |
| npm 依存の侵害 | **実行時・ビルド時ともに npm 依存ゼロ**。Node 標準ライブラリだけでビルドする。`package.json` に dependencies を持たない |
| データ（事案の事実テキスト）経由のXSS | ビルド時に全出力をエスケープ。クライアントJSは `innerHTML` を使わず DOM API で構築。CSP で `require-trusted-types-for 'script'` を指定し、文字列をHTMLとして流し込む経路を**ブラウザが遮断**する |
| 外部スクリプト・CDN の侵害 | 外部リソースを一切読まない。CSP `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; connect-src 'self'; manifest-src 'self'` |
| `<base>` の注入、プラグイン | CSP `base-uri 'none'; object-src 'none'; form-action 'none'` |

GitHub Pages は HTTP ヘッダを設定できないため、CSP は `<meta http-equiv>` で指定する。`frame-ancestors` は meta では無効なので、クリックジャッキング対策は「ログインも操作もない静的ページなので被害がない」として**受け入れる**。HSTS は `github.io` がプリロード済み。

### T3 偽サイト・なりすまし（A3）

| 経路 | 対策 |
| --- | --- |
| サイトを丸ごとコピーして偽の番号を載せる | 完全には防げない。**受け入れつつ軽減**：サイト内に「本物のURLは `kyritk.github.io/jibun-joho-taisaku` だけ」と明記。メールを送らない（企画書どおり）ので「このサイトからのメール」自体が偽物と言える。入力欄を持たない（パスワード・個人情報を入れる場所がない設計そのものが対策） |
| 似たドメインの取得 | 独自ドメインを持たないので、`github.io` 以外を名乗るものは偽物と説明できる |

### T4 端末内データの漏えい・悪用（A2）

| 経路 | 対策 |
| --- | --- |
| 共有端末で他人に見られる | 保存するのはサービスID・完了日・最終確認日だけ。「この端末の記録を消す」ボタン。氏名等は保存しない |
| 悪意あるブラウザ拡張 | 拡張からは防げない。保存データを最小にすることで被害を限定（受け入れる） |
| 引き継ぎコードの盗み見 | コードは暗号化しない（鍵の受け渡しが要るため）。コードに含まれるのはサービスIDと完了日のみ。画面に「他人に見せない」と注意書き |
| URLの `#s=` による選択の持ち込み | 外部から来たリンクで選択が勝手に変わる。ユーザーに「追加しました」と見せ、サービスIDの存在チェックを通したものだけ反映 |

### T5 古い情報を表示し続ける（A1）

| 経路 | 対策 |
| --- | --- |
| Service Worker のキャッシュで続報が届かない | フェーズ1では **Service Worker を置かない**。manifest のみで「ホーム画面に追加」を実現する（iOS は SW 不要、Android Chrome も現在は不要）。将来入れる場合も `data.json` はネットワーク優先にする |
| ブラウザのHTTPキャッシュ | `data.json` のURLにビルド時のハッシュを付けず、代わりに `generated_at` を表示。ページ本体は毎回取得される |
| 承認者が続報に気づかない | 週次の目視確認（企画書の運用）。将来：公式URLの変更検知 |

### T6 第三者への情報送信（A2）

| 経路 | 対策 |
| --- | --- |
| アクセス解析・フォント・CDN | 一切使わない。CSP で技術的に禁止 |
| 外部リンクのリファラで「このサイトを見ていた」ことが漏れる | `<meta name="referrer" content="no-referrer">` と `rel="noopener noreferrer"` |
| GitHub Pages のアクセスログ | GitHub がIPアドレス等を記録する。利用者には制御できないので**プライバシーポリシーに明記**して受け入れる |

### T7 公開パイプラインの悪用（A4）

| 経路 | 対策 |
| --- | --- |
| フォークからのPRでワークフローが秘密情報にアクセス | 秘密情報を持たない。PR時のワークフローは `contents: read` のみ |
| ビルドスクリプトが外部にアクセス | ビルドはネットワークを使わない（ファイル読み書きのみ） |
| main への force push で履歴（訂正履歴）が消える | ブランチ保護：force push 禁止、削除禁止、直線履歴 |

### T8 法的・運用上のリスク（A1, A3）

| 経路 | 対策 |
| --- | --- |
| 企業からの訂正・削除要請に応じられない | 訂正窓口（GitHub Issues と連絡先）を公開。否定された事案は `status: denied` にして取り下げ表示、履歴は Git に残る |
| まとめサイトの文章を転載してしまう | `facts` は事実項目のみ。文章はすべて自分で書く。出典は公式発表URL |
| 「あなたの情報が漏れた」と断定して誤認させる | 文言の原則2。利用規約・注意書きで網羅性・即時性を保証しないと明記 |

### 受け入れるリスク（対策しないと決めたもの）

- サイトの丸ごとコピー（T3）。構造上防げない。
- ブラウザ拡張による端末内データの読み取り（T4）。
- GitHub の障害によるサイト停止。代替配信は持たない。
- クリックジャッキング。操作対象がないため実害がない。

## 4. 対策の実装一覧（チェックリスト）

- [x] 実行時・ビルド時の npm 依存ゼロ（`package.json` に dependencies なし）
- [x] 公式ドメインの許可リスト `data/official-domains.json` と、CI での検査（`scripts/validate.mjs`）
- [x] クライアントJSで `innerHTML` を使わない（DOM API のみ）
- [x] CSP（meta）：`default-src 'none'`、`script-src 'self'`、`require-trusted-types-for 'script'`、`base-uri 'none'`、`object-src 'none'`、`form-action 'none'`
- [x] `referrer: no-referrer`、外部リンクに `rel="noopener noreferrer"`
- [x] Service Worker なし（manifest のみ）
- [x] GitHub Actions：SHA固定、最小権限、シークレットなし、PR時は読み取りのみ
- [ ] GitHub：2要素認証（アカウント設定。手動）
- [x] ブランチ保護：main への直接push禁止、force push 禁止、CI必須（`gh api` で設定）
- [x] SECURITY.md（脆弱性の報告先）とプライバシーポリシー（端末内保存の項目、GitHub のログ）
- [x] 承認フロー：`drafts/` → 目視 → `approved/`。CI は `approved/` だけをビルド
- [x] アイコン：`assets/icons/*.svg` を信頼できない入力として扱い、ビルドで `<path>` の `d`・`fill-rule` だけを取り出して HTML 内スプライトにする（外部SVG・data: URI・絵文字は不使用。`check-dist.mjs` が `<use href="#i-…">` 以外と絵文字を検出）

## 5. 見直しのタイミング

次のいずれかが起きたら、この文書を更新する。
- メール通知やサーバー同期など、サーバー側を持つ機能を入れるとき（資産と境界が増える）
- 独自ドメインを取るとき（T3 の前提が変わる）
- Service Worker を入れるとき（T5）
- 外部の人が PR を送るようになったとき（T1・T7 の運用を実際に回す）
