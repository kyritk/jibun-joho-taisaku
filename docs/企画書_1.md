# じぶんの情報対策 企画書

Nov 7, 2026

## 背景と課題

2026年の日本では、企業からの個人情報漏えいが過去最悪のペースで続き、個人は「自分が対象か」「何をすればいいか」を自力で判断するしかない状況にある。

| 指標 | 数値 | 出典 |
| --- | --- | --- |
| サイバー攻撃による情報漏えい事案（2026年1〜10月） | 661件。前年通年の428件を上回る | [MM総研](https://www.m2ri.jp/release/detail.html?id=741) |
| 個人情報保護委員会への不正アクセス漏えい報告（2026年4月1日〜10月16日） | 2,094件、延べ約2.6億人分。10月は16日間で830件 | [nippon.com](https://www.nippon.com/ja/articles/-/56652) |
| 1,000万件超の事案（2026年秋） | skyticket約1,464万件、焼肉きんぐ約1,078万件、ソースネクスト約2,252万件など | [humanhacker.ai](https://humanhacker.ai/media/summary/) |
| 特殊詐欺被害（2026年上半期） | 1,816億円（前年同期比51.7%増）。ニセ警察詐欺が507.9億円 | [警察庁発表の報道](https://scan.netsecurity.ne.jp/article/2026/08/07/55883.html) |

個人が直面している問題は3つある。

1. 複数の企業から漏えい通知がばらばらに届き、自分がどの事案の対象かを一元的に把握できない。
2. 「免許証画像が漏れた」と「メールアドレスが漏れた」では取るべき行動がまったく違うが、その翻訳を本人がしなければならない。IPAの相談窓口には「通知は来たが、どうすればよいかわからない」という相談が多数寄せられている（[IPA、2026年10月26日](https://www.ipa.go.jp/security/anshin/attention/2026/mgdayori20261026.html)）。
3. 主な被害者は高齢層で、本人より家族が動くことが多い。ニセ警察詐欺は被害額・認知件数ともに70代が最多。

既存の対策は、公的機関のPDF（読んで自分で判断する前提）か、個人情報を預ける海外製の監視サービス（HIBP、Mozilla Monitorなど。日本企業の事案の収録が薄い）に限られる。

## コンセプトと唯一性

**じぶんの情報対策** は、使っているサービスを選ぶだけで、自分に関係ある漏えいと自分がやることだけが揃い、対策済みの安心な状態に到達できるツールである。

タグライン：**使っているサービスの漏えいと、やることだけ**

### 唯一性

| 観点 | 既存の監視型（HIBP、ノートン、トレンドマイクロなど） | 公的機関・まとめサイト（IPA、警視庁、security-karte.jp） | じぶんの情報対策 |
| --- | --- | --- | --- |
| 対象 | 世の中の流出データ・ダークウェブ | 世の中の公表事案、一般的な対策 | 自分が使っているサービスの公表事案だけ |
| 入力 | メールアドレス、氏名、カード番号などを預ける | 不要 | 利用サービスの選択だけ。既定では何も預からない |
| 出口 | 「漏れている」という検知結果 | 読んで自分で判断する資料 | 1カード1行動の「やること」と、完了したら「対策済み」になる状態 |
| 日本の事案 | 薄い（HIBPで「Japan」を含む侵害は7件） | 厚い | 厚い（公式発表を目視承認したものだけ） |

Googleは「効果的な対処法を示せていない」というフィードバックを理由に、2026年2月にダークウェブレポートを終了した（[一創](https://www.issoh.co.jp/column/details/3085/)）。検知して知らせるだけでは価値が薄く、「次の1行動」に落とすことに価値がある。

### 価値の中心

プロダクトの本体は「やることカード」ではなく、**サービス選択 × 承認済み事案DB × 続報追跡** のパイプラインである。カードはその出口にすぎない。LLMに通知メールを貼り付けても得られないのは、次の3つである。

1. 自分が対象の事案だけを、見逃していても教えてくれること。
2. 「おそれ」→「確定」→「対象者の絞り込み」という続報を追い続けてくれること。
3. 開発者が公式発表を目視で確認した、信頼できる根拠だけを示すこと。

## ユーザー体験

登録から対策完了まで、ユーザーがすることは「サービスを選ぶ」「カードを順に終える」の2つだけである。

1. **初回：使っているサービスを選ぶ。** コンビニ、通販、旅行、カーシェア、カラオケ、通信など生活カテゴリのアイコン一覧から選ぶ。企業名ではなく「焼肉きんぐのアプリ」「タイムズカー」のように、ユーザーが認識している呼び名で並べる。選択は端末内に保存し、サーバーには送らない。
2. **「じぶんのやること」画面を見る。** 選んだサービスの承認済み事案だけが表示される。前回の訪問以降に増えた事案は未読として強調する。
3. **事案を開き、やることカードを順に終える。** 漏れた情報の種類ごとに1カード1行動で表示する。「同じパスワードを使っている他のサービスも変える」「カード裏面の番号に電話する（番号を表示）」など。専門用語は使わない。「すでに申し込んだ人は出し直さない」といった、やらなくていいことも示す。
4. **全カードを終えると「いまは対策済みです」になる。** 続報（おそれ→確定、対象の絞り込み）が出ると、必要なカードだけが再び未完了に戻る。
5. **将来：メール通知。** MVPでは提供しない。運用費を抑えるため独自ドメインを取らず、メール送信は将来の検討事項とする。
6. **任意：家族の代理設定。** 子が親の使っているサービスを自分の端末にも登録し、親の分の「じぶんのやること」を確認できるようにする。「親にこう声をかけて」という台本を添える。

### 再訪の導線

通知をプッシュしないので、見に来てもらう仕組みが要る。

- 事案別の公開ページ（「タイムズカーの情報漏えい｜じぶんの情報対策」）。漏えい直後に「サービス名＋漏えい」で検索する人を受け止め、末尾で「このサービスを登録しておくと、続報がわかります」と誘導する。
- 未読バッジ。端末内の最終確認日時と事案DBを比べて新着を強調する。
- ホーム画面への追加案内。通知のためではなく「次に見に来やすくする」ための案内なので、ハードルが低い。

### 端末内保存の注意

機種変更やブラウザのデータ削除で選択が消える。対策は、選択内容をコード化して書き出し・読み込みできる軽い引き継ぎ機能。サーバー同期は持たない。

## やることカード

カードは漏れた情報の種類ごとに用意し、すべてに公的な根拠を付ける。1枚1行動、専門用語なし、完了でチェックできる。

| 漏れた情報 | カード（1枚1行動） | 根拠 |
| --- | --- | --- |
| ID・パスワード | ①そのサービスのパスワードを変える ②同じパスワードを使っている他のサービスも変える ③二段階認証を設定する | [IPA 2026年10月26日](https://www.ipa.go.jp/security/anshin/attention/2026/mgdayori20261026.html) 2.2節 |
| クレジットカード番号 | ①カード裏面の番号に電話して停止・再発行を相談する ②しばらく明細を確認する ③身に覚えのない認証には応じない | IPA 2.3節、[警視庁 都民向け資料](https://www.keishicho.metro.tokyo.lg.jp/kurashi/cyber/joho/information_leak.files/tomin.pdf) |
| メールアドレス・電話番号・住所・氏名 | ①突然届くメール・SMSのリンクは開かない ②その会社を名乗る「おわび」「返金」メールも疑う ③国際電話の着信を止める（固定電話は0120-210-364） | IPA 2.4節、警視庁資料 |
| 運転免許証などの本人確認書類の画像 | ①信用情報機関（JICC・CIC・全国銀行個人信用情報センター）に本人申告する ②身に覚えのない契約書類が届いたら送付元と警察に連絡する ③すでに申し込んだ人は出し直さない | IPA 2.5節、[@IT 2026年11月2日](https://atmarkit.itmedia.co.jp/ait/articles/2611/02/news009.html) |
| 銀行口座 | 金融機関に連絡し、ネットバンキングのパスワード変更と出金履歴の確認をする | @IT、警視庁資料 |
| マイナンバー | 市区町村か「マイナンバー総合フリーダイヤル」0120-95-0178に相談する。不正に使われるおそれがある場合に限り番号を変更できる | @IT、政府広報オンライン |
| 金融資産・家族構成・住所 | ①訪問業者にはドアを開けずに対応する ②「お金の話が出たら詐欺」と覚えておく ③警察相談#9110 | 警視庁資料（強盗・悪質訪問業者の項） |
| 病歴・診療の情報 | 公式資料に個別の推奨行動がない。「医療機関を名乗る連絡を疑う」にとどめ、相談窓口へ誘導する | 要追加調査 |

### カード設計の原則

- 「あなたの情報が漏れました」と断定しない。「○○社が漏えい（のおそれ）を公表しました。対象かは○○社からの連絡で確認してください」と書く。
- 電話番号やURLは、開発者が承認した公式のものだけを表示する。企業の通知メールに書かれたリンクや番号は転記しない。
- 先頭のカードは常に「その会社を名乗るメールのリンクは押さない」。流出元を装う「おわび」メールが実際に出回っている。
- カードはWeb上で表示する。メール通知には載せない。

## データ運用

事案DBは「公式発表を開発者が目視承認したものだけ」を公開する。速報性より正確性を優先し、誤通知を出さないことを最優先にする。

### 対象の絞り込み

全件は追わない。掲載基準は「会員1万人以上の消費者向けサービス」または「カード・パスワード・本人確認書類・口座のいずれかを含む事案」で、企業が公式に発表したもの。

- security-karte.jpの消費者向け漏えいは2026年1月〜11月6日で230件、月平均20件強。1件ずつ目視承認しても週に数件〜10件の作業量で回る。
- 個人情報保護委員会への10月の報告830件のうち588件は10万人以下で、BtoBや委託先の重複を含む。消費者が「自分ごと」にできる事案はその一部にすぎない。

### 収集から公開までの流れ

1. **発見**：まとめサイトのRSS（security-karte.jp、Security NEXT、ScanNetSecurity）と企業のプレスリリースを日次で確認する。まとめサイトは「新着を知るきっかけ」にだけ使う。
2. **一次資料を開く**：企業の公式発表（プレスリリース、お知らせページ）を開き、そのURLを記録する。
3. **構造化の下書き**：LLMで「企業名・サービス名・公表日・漏れた情報の種類・件数・おそれか確定か・公式URL」を抽出する。文章は転載せず、事実項目だけを取る。
4. **目視承認**：開発者が公式発表と見比べ、PRをマージすることで承認する。マージ前は公開されない。
5. **公開**：マージをきっかけにGitHub Actionsが公開JSONと事案別ページを生成し、GitHub Pagesに配置する。
6. **続報の追跡**：第2報以降で「おそれ→確定」「対象者の絞り込み」「漏れた情報の追加」があれば更新し、該当カードを未完了に戻す。否定された場合は訂正履歴を残して取り下げる。

| 項目 | 例 |
| --- | --- |

| 運営会社 | タイムズモビリティ（パーク24） |
| 公表日・続報日 | 2026年9月28日、第2報10月3日 |

### サービスマスタ

消費者向けの主要サービス約100件から始める。通称名、運営会社、ロゴ、パスワード変更ページのURL、公式の問い合わせ電話番号を手作業で登録する。ユーザーからの「このサービスも追加して」を受け付ける窓口を置く。

## 技術構成

MVPはGitHub Pagesの静的配信だけで成立させる。サーバー側にユーザーデータを一切持たず、独自ドメインも取らない（ユーザー名.github.io/リポジトリ名 を使う）ので、運用費はゼロになる。

| 層 | 構成 | 持つデータ |
| --- | --- | --- |
| 匿名利用（既定） | PWA（Next.jsの静的エクスポートなど）と公開JSONの事案DBをGitHub Pagesから配信する。サービス選択と最終確認日時は端末内（localStorage）。「じぶんのやること」画面はブラウザ側で選択と事案DBを突き合わせて計算する | サーバーには何も持たない |
| メール登録者（任意） | MVPでは提供しない。GitHub Pagesにはサーバー処理がないので、将来入れる場合は別のバックエンド（AWS LambdaとDynamoDBなど）が要る | メールアドレス、選択したサービスID、登録日時のみ |
| 事案DB・公開ページ | 事案データはリポジトリ内のファイル。LLMの下書きをPRにし、開発者がマージすることが承認になる。GitHub Actionsで公開JSONと事案別ページを生成し、Pagesへ配置する。訂正履歴はGitの履歴として自動的に残る | 公式発表に基づく事実項目と公式URL |
| メール配信 | MVPでは提供しない。将来入れる場合は独自ドメイン＋SPF・DKIM・DMARC＋送信サービス（Amazon SESなど）が必須 | 送信ログ（最小限） |
| LLM | 事案の構造化の下書きのみ。承認前のデータにしか触れない | ユーザーデータは渡さない |

### GitHub Pagesの制約と対応

- 無料プランではリポジトリを公開にする必要がある。事案DBもコードも公開前提なので支障はないが、承認前のデータはPRやブランチに置き、mainには承認済みだけを入れる。
- サーバー処理ができない。メール通知や家族間の同期など、将来サーバーが要る機能は別のバックエンドで補う。
- URLがサブパス配下になるので、PWAのmanifestとService Workerのスコープをそのパスに合わせる。
- 転送量は月100GB、ビルドは1時間10回が目安。個人開発の規模では届かない。

### メール通知はMVPに入れない

運用費を抑えるため、独自ドメインを取らない。ドメインなしではSPF・DKIM・DMARCを設定できず、迷惑メール判定を避けられないので、メール送信自体を見送る。再訪は事案別の公開ページと未読バッジで促す。

将来メール通知を入れる場合の原則は決めておく。本文にリンクを一切置かず、送信者名とアドレスを固定し、登録時に「この名前から届きます」と見せる。

### 使わない技術

- Webプッシュ通知：iOSは「ホーム画面に追加」と操作をきっかけにした許可が必須で、高齢者には壁が高い。LINEのアプリ内ブラウザからは追加できない。
- LINE Messaging API：無料枠は月200通で、登録者200人で1事案さえ全員に届かない。有料プランは月5,000円から。
- HIBPのメールアドレス検索API：有料（最安で月4.39ドル・年払い）で、個人情報を預からない方針と合わない。Pwned Passwords（k-匿名、無料）は後回しの補助機能候補。

## 法務・運用チェックリスト

最大のリスクは「誤掲載の放置」と「まとめサイトへの依存」である。以下は一般的な整理で、個別の法律相談ではない。

- [ ] 掲載の根拠を企業の公式発表に限る。まとめサイトの記事やデータは複製・再配信しない（Security NEXTは許可のない引用・転載・複製・第三者提供を禁止、ScanNetSecurityは無断転載禁止）。
- [ ] 事実項目だけを構造化し、文章はすべて自分で書く。公式発表へのリンクを必ず付ける。
- [ ] 「漏えい」と「漏えいのおそれ」を区別して表示する。続報で否定された事案は訂正履歴を残して取り下げる。
- [ ] 「あなたの情報が漏れました」と断定しない。企業からの個別連絡で確認するよう案内する。
- [ ] 訂正・削除の問い合わせ窓口を公開する。企業からの指摘には迅速に対応する。
- [ ] 政府系資料（IPA、個人情報保護委員会）は政府標準利用規約2.0に沿って出典を明記する。「国が作成した」と誤認させる表現を避ける。警視庁資料は要約とリンクにとどめる。
- [ ] プライバシーポリシーに、MVPではサーバーに個人情報を保存しないこと、端末内に保存する項目（サービス選択、最終確認日時）を明記する。
- [ ] （将来メール通知を入れるとき）特定電子メール法に沿って、ダブルオプトイン、送信者表示、ワンクリック解除を実装する。
- [ ] 利用規約で「一切責任を負わない」と書かない（消費者契約法8条で無効になりうる）。「故意・重過失を除き、責任は○○を上限とする」形にし、通知の網羅性・即時性を保証しないことを明記する。
- [ ] 通知メールのリンクや電話番号を、企業の通知メールから転記しない。承認済みの公式情報だけを表示する。
- [ ] 未確認の攻撃者情報（ARTEXなど）を個別の事案と結びつけない。
- [ ] 「じぶんの情報対策」をJ-PlatPatで検索し、同一・類似の商標がないか確認する。ドメインの空きを確認する。
- [ ] security-karte.jpとhumanhacker.aiの利用規約の本文を確認する。RSS利用や連携の可否は運営者に直接問い合わせる。

## やらないこと

個人開発で実現できる範囲に絞るため、次は最初から対象外とする。サイト上でも正直に明記する。

| やらないこと | 理由 |
| --- | --- |
| ダークウェブ監視、未公表の漏えいの検知 | クローラの維持コストと法的リスクが個人の手に余る。対象は「企業が公表した漏えい」のみ |
| 氏名・電話番号・カード番号・本人確認書類の預かり | 漏えい時の責任を個人で負えない。預かるのは任意のメールアドレスとサービス選択だけ |
| 通知メールの貼り付けからのやること生成 | LLMに直接聞くのと変わらず強みがない。偽メールの貼り付けやPII送信のリスクもある |
| フィッシングメールのリアルタイム判定 | メールへのアクセス権限が必要で、心理的ハードルが高い |
| 有人相談 | 対応できない。電話番号と公式窓口への導線に徹する |
| 全事案の網羅 | 消費者に関係ない事案が多い。影響の大きい消費者向け事案に絞る |
| Webプッシュ通知、LINE通知、メール通知（MVP） | 技術構成に記載の通り。独自ドメインを取らないため、メールも送らない |

## MVPロードマップと次のアクション

コードを書く前に「やることカード」と「事案データ」の実物で価値を検証し、通る見込みが立ってから実装する。

### 今週やること

開発はVS Code＋Claude Codeで行う。この企画書をMarkdownでエクスポートしてリポジトリに置き、CLAUDE.mdから参照させる。

- [ ] 「じぶんの情報対策」をJ-PlatPatで検索し、ドメイン候補の空きを確認する
- [ ] やることカード8種類を書き、各カードに根拠URLを付ける
- [ ] 直近の大規模事案20件（タイムズカー、skyticket、焼肉きんぐ、ソースネクスト、KDDI系など）を公式発表から構造化する
- [ ] security-karte.jpの運営者にRSS利用と連携の可否を問い合わせる
- [ ] 身近な非IT層3〜5人に、モックを見せる約束を取る
- [ ] GitHubリポジトリを作り、企画書のMarkdownとCLAUDE.md（コンセプト、やらないこと、カード設計の原則、承認フローを要約）を置く

- GitHub Pagesの2026年時点の利用制限（転送量・ビルド回数）の最新値
